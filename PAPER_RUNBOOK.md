## Crash/restart behavior

The runtime persists the rebalance intent before sending orders. An unfinished rebalance is resumed from broker-confirmed positions rather than replayed from an assumed local position.

The automated crash-after-fill test is part of the pytest suite. The most recent measured scenario is also recorded in:

```bash
cat results/paper/crash_recovery.json
```

A completed rebalance must return `ALREADY_DONE` on repetition and submit no new orders.

## Roostoo validation order

Before any paper order, validate in this order:

1. `/v3/serverTime`
2. `/v3/exchangeInfo`
3. `/v3/ticker`
4. authenticated `/v3/balance`
5. `/v3/pending_count` / pending order query
6. `/v6/short_positions`
7. verify symbol availability, precision, minimum order values, and account state
8. dry-run target/order construction
9. only then consider a deliberately small paper-order validation

Run the read-only helper with current credentials:

```bash
PYTHONPATH=src python research/run_roostoo_readonly.py
```

No real order should be submitted merely to test connectivity.

## Halt conditions

Do not add new risk when any of the following is true:

- stale or invalid market data;
- incomplete warm-up;
- research/live parity failure;
- unknown pending orders;
- unreconciled broker state;
- invalid account equity/cash/collateral;
- exposure-cap violation;
- unfinished rebalance whose broker state cannot be reconstructed;
- API authentication/time synchronization failure.

A halt means stop adding risk; it does not automatically mean liquidate all positions.
